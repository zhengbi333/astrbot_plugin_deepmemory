# alpha-0.83

## 第 3 轮迭代（deepmemory）：清空上下文前先抢救记忆

### 诊断（用真库只读快照 + 日志定位，不靠猜）

| 证据 | 说明 |
|---|---|
| `memories` 表**只有 1 条**（9-06 写入的身份记忆） | 长期记忆几乎为空 |
| `timeline` **13 条全部 `summarized=0`** | 自动提炼**从未运行过** |
| 日志反复出现「**检测到清空上下文指令，已清空未总结缓存: removed=4**」 | 每次清空上下文，未总结的对话被**直接丢弃** |
| `injection_logs` 有 `selected_memory_ids`、`injection_chars=1800` | 召回/注入链路**是通的**（不是这部分的问题） |
| 提炼模型 `summary.provider_id` 为空 | **不是故障**：`_llm_json` 有回退链（主模型 → 备用 → 当前会话模型），实机已确认 |

**结论**：记忆攒不起来不是"没聊天"那么简单——**清空上下文会把还没提炼的对话直接扔掉**。
累计不到 `trigger_event_count`（默认 8）就清零，于是自动记忆永远触发不了。
真人不会因为你让他忘掉刚才的对话，就忘记你昨天说过要买牛奶。

### 修复

`handle_reset_command` 里，清空**之前**先抢救一次：

```
检测到清空指令 → 【新】若有未总结事件 → 提炼一次（落成记忆）
                → 再清空未总结缓存（照旧）
```

| 设计点 | 取值 / 行为 |
|---|---|
| 开关 | `summary.before_reset_enabled`（默认**开**） |
| 超时 | `summary.before_reset_timeout_seconds`（默认 25，限 5~120）；**超时不阻塞清空** |
| 省调用 | 没有未总结事件时**根本不调用**提炼（不浪费一次模型调用） |
| 失败隔离 | 读库失败 / 提炼异常 / 模型无输出 → 只记日志，**清空照常进行** |
| 可观测 | 日志区分「已提炼 N 条」「判定无新信息」「超时未保存」「失败」 |

## 验证

- **第二十六批（新）14/14**：正常抢救（调用提炼 + 返回条数）、无事件时不调用（省调用）、
  开关关闭 / 总提炼关闭时不调用、**超时兜住（约 5s 返回且不阻塞）**、提炼抛异常 / 读库失败均只标记失败、
  提炼无输出与"判定无新信息"都返回 0、静态 3 项 + 配置默认开启
- **第二十七批（真链·新）4/4**：用 deepmemory 自己的提炼提示词 + 一段真实对话喂给真实 DeepSeek →
  输出可解析、含非空 content、**关键事实（医院复查 / 牛奶 / 离心机）至少覆盖两个**：
  > content：**证毕明天上午九点需去医院复查，要空腹抽血，并请阡墨提醒买牛奶（家里没了），阚墨答应晚上提醒。证毕本周想修实验室那台老出问题的离心机……**
- **回归**：storyteller 十八批非真链 413/413、真链 61/61 未受影响（本轮只动 deepmemory）

## 顺带留下的结论（给后续轮）

1. 记忆库空的主要原因是「**对话量少 + 清空即丢弃**」；本轮已堵住后者，前者要靠正常使用积累。
2. 用户的 `summary.provider_id` / `fallback_provider_id` 都为空——虽然能回退到当前会话模型，
   但**显式配一个**会更稳、更省（避免每轮都走回退链）。面板上可直接填。
3. timeline 里 `role=bot` 的比例偏高（10/13）——因为拆条发送会把一句话记成多条；
   后续可考虑把"同一轮的多条 bot 消息"合并后再提炼，让记忆更紧凑。
